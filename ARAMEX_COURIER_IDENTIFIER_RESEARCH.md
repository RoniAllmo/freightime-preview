# Aramex Commercial Parcel and Courier Identifier Research

## 1. Research purpose

This document researches Aramex commercial parcel and courier tracking
identifiers to inform a future, separately authorized decision about
whether and how the FreighTime Single-input tracking router could
recognize Aramex shipment identifiers. This is a research-only task. No
production detection code, regular expressions, or router/UI integration
is implemented here. Findings must be evaluated against
`CLAUDE.md` and `PRODUCT_SPEC.md` before any implementation is authorized.

## 2. Scope and freight exclusion

**In scope:** Aramex parcel shipments, Aramex Express/courier shipments,
Aramex shipment numbers, Aramex airway-bill/waybill numbers used for
parcel tracking, Aramex public shipment tracking, the Aramex Shipment
Tracking API, and the Aramex Shipping Services API only insofar as it
defines shipment-number allocation or structure.

**Explicitly excluded:** freight forwarding, air cargo master AWBs, ocean
freight, house air waybills, house bills of lading, container tracking,
freight booking references, customer references unrelated to parcel
tracking, logistics/warehousing references, EMS, UPU S10, DSV, UPS, DHL,
and FedEx. Where a source mixed freight and parcel/courier terminology
(a recurring pattern in Aramex documentation, which serves both freight
and parcel/express customers under one brand), only the parcel/courier
context is analyzed; freight-only material is noted solely to exclude it.

## 3. Aramex parcel and courier products

Aramex operates as a combined logistics group offering express/parcel
shipping (its historic core "International Express" business), domestic
courier delivery, and freight forwarding/logistics services under the
same corporate brand and, in public materials, sometimes the same
tracking portal. This research addresses only the express/courier/parcel
side. No evidence was found (or sought) that would distinguish separate
tracking-number formats between Aramex Express international parcels
and Aramex domestic courier shipments; both are treated here as a single
undifferentiated "Aramex shipment number" scope pending stronger evidence.

## 4. Official public tracking interface

Aramex's public tracking pages (e.g. `aramex.com/<locale>/track/shipments`
and `aramex.com/<locale>/track/results`) accept a shipment number as an
input parameter. A search-engine-indexed reference to the public tracking
results page showed a `ShipmentNumber` query-string parameter carrying an
all-numeric value of approximately eleven digits. **This specific indexed
example is not reproduced in this document**: because it was found via a
public search-engine index of a live tracking-results URL, it cannot be
confirmed to be a placeholder or test value rather than a real customer
shipment number, and the task's test-fixture policy prohibits treating
values copied from public tracking results as safe. Its existence is
recorded only as structural evidence that the public interface uses a
parameter literally named `ShipmentNumber` carrying a numeric string of
roughly ten to eleven digits — not as a usable example value.

Direct access to `aramex.com` public tracking and help pages was blocked
in this environment (see Section 15 for the access-limitation pattern),
so the public tracking page's own input-validation rules (if any) could
not be directly inspected.

## 5. Official Tracking API

Aramex publishes a "Shipments Tracking API" (also referred to as the
Tracking API), documented in an official manual titled *"Your Guide to
Embedding Aramex's Tracking API."* Per search-synthesis referencing this
official manual's structure, the API's `TrackShipments` operation accepts
client authentication information, a transaction block, and a list of
shipment numbers ("Shipments"), returning tracking results for each. The
API is explicitly designed to accept **multiple** shipment numbers in a
single request (an array/list), not only one.

No direct access to the manual's PDF was possible in this environment (see
Section 15), so the exact XML/WSDL element names, data types, and any
declared length or pattern constraints for the shipment-number field
could not be directly verified. These remain unread official material.

## 6. Official Shipping Services API

Aramex also publishes a "Shipping Services API," documented in an official
manual titled *"Aramex's Guide to Embedding the Shipping Services API."*
Per search-synthesis referencing this manual, its shipment-creation
operation (`CreateShipments`) returns, on success, an assigned AWB
number (referred to in synthesized summaries as an "AWB ID") that becomes
the shipment's tracking identifier; a `Reference` field is also present
but carries the customer-supplied reference value, not the AWB/tracking
number, and is out of scope per this task's exclusion of customer
references. This indicates that Aramex-issued shipment numbers are
system-generated by Aramex at shipment-creation time, not
customer-chosen — consistent with courier industry norms, but not
independently confirmed against the manual's own text in this session.

No direct access to this manual was possible in this environment (see
Section 15).

## 7. Official shipment-number terminology

Search-synthesis referencing Aramex's own tracking-guide and API-manual
titles consistently uses the term **"shipment number"** as the primary
label for the identifier used with the Tracking API's `Shipments`
parameter list. The term **"AWB" (air waybill) / "AWB number"** also
appears in the same official-manual context (the Tracking API's own
title references "AWB numbers," and the Shipping Services API's creation
response is described as returning an "AWB number/ID"), suggesting Aramex
uses "shipment number" and "AWB number" largely interchangeably for its
own parcel/courier identifiers, distinct from a separate freight-only
term. No source directly confirmed a formal definition distinguishing the
two terms. No evidence was found for the terms "tracking number" or
"waybill number" (without "air") being used as an official Aramex-defined
field name, though they appear informally in secondary/aggregator
material.

## 8. Tracking-request schema

Per search-synthesis referencing the official Tracking API manual's
structure, the `TrackShipments` request accepts: client authentication
information, a transaction identifier block, and a `Shipments` list of
shipment-number values. No source reached in this session provided the
actual XSD/WSDL type declaration (e.g. `xs:string`, `minLength`,
`maxLength`, or `pattern` facets) for the shipment-number element. This
schema-level detail remains unverified official material — the manual
exists and is officially Aramex-controlled, but its content was not
directly inspected in this session due to the access blocks described in
Section 15.

## 9. Published length and character rules

No officially confirmed, source-verified length or character-set rule was
found. Secondary, non-Aramex-controlled tracking aggregators (not
authoritative per this task's source rules) offer mutually inconsistent
claims — variously describing Aramex tracking numbers as 10 digits, 10–11
digits, 10–15 digits, or "10, 11, 12, or 20 digits," with one aggregator
also claiming some international shipments use alphanumeric characters.
These claims are recorded only to illustrate the lack of a stable,
corroborated public consensus; none is treated as evidence for
implementation purposes.

## 10. Prefix evidence

No distinctive Aramex prefix (letter or digit sequence) was found in any
source reached in this session, official or secondary. Unlike UPS's
confirmed "1Z"/"1R" prefixes, no equivalent evidence exists for Aramex.

## 11. Shipment-number range allocation

Per search-synthesis referencing the Shipping Services API manual (not
directly read), shipment numbers ("AWB numbers") appear to be generated
and assigned by Aramex's own system at the time `CreateShipments` is
called, rather than allocated to customers as pre-reserved ranges. No
source described a publicly documented numbering scheme, account-based
range allocation, or country/service-based numbering block. This remains
an unverified inference from an unread official document, not a confirmed
fact.

## 12. Check-digit evidence

No Aramex-specific check-digit algorithm was found in any source. A
generic, carrier-agnostic 11-digit "XXX-XXXXXXX-Y" air waybill format with
a modulus-7 check digit was found in general aviation-industry reference
material — this describes the IATA-style master air waybill numbering
convention used industry-wide (and already independently implemented in
this project's own `detect-awb.js` for air waybills), not an
Aramex-confirmed rule for Aramex's own parcel/courier shipment numbers.
No source connected this generic industry convention specifically to
Aramex's shipment-number system, and per this task's scope it must not be
assumed to apply to Aramex parcel/courier identifiers.

## 13. Official documentation fixtures

No official Aramex documentation example, sample shipment number, or
explicitly-labeled test fixture was directly inspected in this session, so
none can be recorded here as a verified example. The single numeric value
observed in a search-indexed public tracking URL (Section 4) is
deliberately not reproduced, since it cannot be confirmed as a
documentation-sanctioned test value rather than a real customer shipment.

Search results referenced the existence of Aramex-published **sandbox API
test credentials** (a username, password, and account identifiers) inside
the official API manuals, intended for developers testing API connectivity.
Per this task's explicit instruction not to use documentation credentials
and not to copy credentials into the repository, these values are
deliberately **not reproduced** in this document; only their existence and
purpose (sandbox authentication testing, not a tracking-number format
example) is recorded.

## 14. Identifier overlap and ambiguity

Because no distinctive Aramex prefix or confirmed structural rule was
found, any purely numeric Aramex shipment number of typical courier length
(roughly 10–15 digits, per uncorroborated secondary claims) cannot be
reliably distinguished from: generic numeric FedEx or DHL tracking
numbers (also unconfirmed in length/format per this project's own FedEx
and DHL research), non-"1Z"/"1R" UPS identifiers, generic numeric order or
reference numbers, or other unrelated numeric strings a user might enter.
This mirrors the same overlap risk already documented for DSV, DHL, and
FedEx in this project's prior research.

## 15. API authentication and browser limitations

Search-synthesis referencing the official API manuals indicates that both
the Tracking API and the Shipping Services API require client
authentication information passed with every request, commonly described
as including: a username, a password, an API/schema version, an account
number, an account PIN, an account entity code, and an account country
code. This is consistent with a server-side, credentialed API design, not
an open/public API.

All direct `WebFetch` and `curl` attempts to `aramex.com` domains in this
session — the Developers Solution Center page (both `/ae/en/` and
`/us/en/` locale variants), the Tracking API manual PDF, the Shipping
Services API manual PDF, and the public help/tracking pages — returned
HTTP 403 (proxy-level connection rejection), the same access-limitation
pattern already observed for `developer.dhl.com`, `developer.fedex.com`,
`developer.ups.com` (partially), `developer.dsv.com`, `upu.int`, and
`ems.post` in this project's prior research phases. No Aramex-controlled
GitHub organization with reachable official specifications was found
(unlike UPS's `github.com/UPS-API`).

Given the credentialed, multi-field authentication scheme described above,
browser-side integration of either Aramex API would require embedding
account credentials in client-side code, which is inappropriate and
already prohibited by `CLAUDE.md` Section 9 and Section 13 regardless of
this research's findings.

## 16. Local detection feasibility

High-confidence local (client-side, credential-free) detection of Aramex
shipment numbers is **not currently feasible**. No distinctive prefix, no
officially confirmed fixed length, no confirmed character-set rule, and no
check-digit algorithm were found in any directly inspected official
source. The only path to a verified Aramex format in this session was via
search-synthesis referencing official manual titles/structure, not by
reading the manuals' actual schema content.

## 17. Proposed safe recognition options

**Option A — recognize only a distinctive, directly verified prefix with
complete official structure.** Not currently applicable: no distinctive
Aramex prefix exists in any source found.

**Option B — recognize an officially verified numeric length as a
possible match only.** Not currently applicable at high confidence: no
official (directly inspected) source confirmed a specific length; only
mutually inconsistent secondary/aggregator claims exist.

**Option C — return several possible-courier matches when a numeric
identifier overlaps multiple courier families.** Structurally available
in principle (the router/detector contract already supports
`possibleCarriers` and `ambiguous` fields), but not meaningfully
actionable for Aramex specifically until at least one courier in the
overlapping set has a confirmed, distinguishing structural rule.

**Option D — do not implement local Aramex recognition; require manual
selection or future authenticated API verification.** Directly supported
by the evidence gathered: no directly inspected official source confirmed
a structural rule sufficient for safe local recognition.

## 18. Proposed detector-result behavior

Not applicable for implementation at this stage — no detector logic is
authorized or created by this task. If a future stage authorizes limited
recognition, any Aramex-matching result would need to follow this
project's existing structured detector-result contract (as already used by
`detect-container.js`, `detect-awb.js`, and `detect-postal.js`):
`identifierType: 'courier'`, an honestly reported `ambiguous: true` state
whenever a numeric match could equally belong to another courier family,
and `possibleCarriers` limited to only what direct evidence supports —
never a forced single-carrier match.

## 19. Open product decisions

- Whether to pursue a stronger direct-access path to the official Aramex
  Tracking API and Shipping Services API manuals (e.g. a differently
  routed fetch, or a project-owner-supplied copy of the PDF) before any
  implementation decision.
- Whether Aramex recognition should be deferred indefinitely (Option D)
  or revisited once official schema content is actually read.
- Whether, across all five researched couriers (DSV, UPS, DHL, FedEx,
  Aramex), only UPS's confirmed "1Z"/"1R" prefix format currently meets
  the evidence bar for any local recognition, and whether the others
  should collectively remain unrecognized pending stronger evidence.
- These decisions require explicit project-owner authorization and are
  not resolved by this research task.

## 20. Recommended next stage and explicit exclusions

**Recommended next stage:** With all five courier candidates (DSV, UPS,
DHL, FedEx, Aramex) now researched, the recommended next stage is a
project-owner review of the consolidated evidence across all five
documents to decide which, if any, courier(s) warrant a future,
separately authorized implementation stage — rather than further
single-courier research. If the project owner wants to keep pursuing
direct evidence, the only clearly promising path identified across the
whole phase is attempting alternate, permitted means of directly reading
the official Aramex PDF manuals (e.g. project-owner-supplied copies, as
was done for the UPU S10 spreadsheet).

**Explicit exclusions confirmed for this task:** no production
JavaScript or regular expression was created; `js/tracking/detect-courier.js`,
`js/tracking/carrier-registry.js`, `js/tracking/router.js`, and `index.html`
were inspected but not modified; no Aramex tracking URL was constructed or
visited; no identifier was submitted to Aramex or any tracking service; no
Aramex recognition rule was approved for implementation; freight
forwarding, air cargo, ocean freight, and all other couriers (DSV, UPS,
DHL, FedEx, EMS, UPU S10) remain out of scope for this document.
